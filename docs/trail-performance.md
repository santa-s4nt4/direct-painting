# Trailの負荷調査（2026-10-25）

対象端末はユーザーのiPad mini（A17 Pro）です。実装・計測はMac Studio / M4 Max / 48GB / Chrome 153で行いました。iPad実機のFPS・上限本数はまだ測定していません。

## 確認できた原因

1. 各レイヤーで毎フレーム4K全体を別の合成先へコピーし、Blurも画面全体で実行していました。細い筆跡でも本数に比例して処理が増えます。Analogの重なり部分ではSpectralの顔料混色も実行します。
2. シークや再構築時、Trailの最初から全筆跡を描き直していました。60秒の筆跡10本を57秒へ戻すテストでは約15万スタンプ、86msの停止が発生しました。短い通常再生が軽くても、長い筆跡の途中で急に遅くなる原因になります。
3. 太い線ではGPUマスクの面積とメモリが増えます。非表示マスクは96MiBを超えると解放するため、3000px・10本のケースでは次のループで7枚を再確保しました。通常再生中の毎フレームの再確保は0件でした。
4. CPUバックエンドの場合は別の問題です。4K・10本のCPU基準描画は約1.5秒/フレームで、60fpsは届きません。画面の「60 fps · GPU / CPU」は設定FPSと方式を示し、実測FPSのメーターではありません。

## 今回の修正

- 2枚の合成先の差分は直前のレイヤー範囲だけなので、その部分だけを同期します。最初のレイヤーでは両方を透明に初期化します。
- Blurの縮小・横・縦のパスを筆跡＋半径の範囲へ制限します。作業用の画像は毎回クリアし、ほかのレイヤーの色が残らないようにしました。
- ライブ描画の4Kマスクは再利用し、表示・Blurの範囲だけを新しい入力点から広げます。
- Trailを再構築するとき、残像寿命1800msより古い履歴を省略します。Returnには適用しません。元の入力点とタイミングは保存したままです。
- 4K全域を覆う極太の筆跡では範囲制限の効果が小さく、GPUメモリの負荷は残ります。

CPU基準との比較に加え、最適化を使わない全画面パスの参照版と、重なり・4K端・シーク・拡大するライブ描画を全画素比較しました。後者の差は0でした。

## 計測結果とメモリ

60秒・96px・10本の57秒へのシークは **86ms → 3.9ms**、スタンプ数は **150,507 → 6,280** でした。これは同じPCでの一度の比較です。短い通常再生の時間は数msの変動が大きいため、全条件で速度が上がったとは判断していません。

96px・Blur16px・10本のケースでは、コピー量が1フレーム約88.13M → 8.06Mピクセル、Blurの処理範囲は約10.37M → 1.06Mピクセルになりました。これは処理ピクセル数で、同じ比率の速度向上を意味しません。

以下は、今回の5秒の経路10本で確保するRGBA8画像の計算値です。プロセス全体の使用量ではなく、ブラウザ・標準フレームバッファ・入力データ等を含みません。経路が広がれば、細い線でもマスクは大きくなります。

| 直径 | 10本のマスク | 共通の作業用画像を含む概算 | 次ループでのマスク再確保 |
| --- | ---: | ---: | ---: |
| 96px | 28.08MiB | 158.60MiB | 0枚 |
| 600px | 77.37MiB | 207.89MiB | 0枚 |
| 3000px | 316.41MiB | 446.93MiB | 7枚 |

内部描画は常に4Kです。表示を10%にしても作業用画像の解像度は下がりません。

## iPad mini A17 Proの暫定目安

Appleの[技術仕様](https://support.apple.com/ja-jp/121456)ではA17 Pro・5コアGPUです。本数の上限は仕様からは決まりません。また、[WebKitの開発者説明](https://www2.webkit.org/show_bug.cgi?id=268816#c10)でもWebContentのメモリ制限は機種により異なるとされています。この説明を現在のGPUメモリの固定上限としては扱いません。

**ハードウェアの限界とはまだ断定できません。** まずアプリ側の再構築の停止を改善しました。下記は面積・混色・メモリを考慮した、実機で確認を始めるための保守的な推測です。測定済みの最大本数・60fps保証値ではありません。

| 筆跡・Blur16px ON・重なりあり | 最初に試す同時表示Trail数 |
| --- | ---: |
| 100px前後、狭い範囲 | 8本 |
| 600px前後 | 4本 |
| 1500〜3000px、広い範囲 | 2本 |

長い経路・大きなBlur・全面での重なり・発熱がある場合は下がります。プロジェクト全体のレイヤー数ではなく、同時に描画する本数で判断します。

## 実機で本数を調べる

iPadの編集画面で **Files → Trail performance** を開き、計測を実行します。同じ端末のほかの編集・出力タブを閉じ、計測タブを前面にしてください。直接開く場合は、編集URLの後ろに `/benchmarks/trail.html` を付けます。ローカルデータの保存やrelay送信は行いません。

- 96 / 600 / 3000px、Blur ON/OFF、1 / 4 / 8 / 10 / 16本（3000pxは10本まで）を計測します。
- 通常再生、重ね描き、最初の一点、シーク、ループ復帰、マスク再確保、60秒の筆跡のシークを記録します。
- GPU処理完了を待って描画時間を測り、通常再生と重ね描きのp95が12ms以内の計測済み本数を表示します。60fpsの16.67msから入力・UI用の余裕を確保するための基準です。
- GPUコンテキストを失った場合は中断し、成功として報告しません。
- 「計測JSONを保存」で結果をダウンロードできます。短時間テストのため長時間の発熱、入力、通信を含む60fpsを保証しません。
